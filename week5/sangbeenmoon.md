## 핵심 내용 요약
### 19장. 정책과 수준
- 컴퓨터 프로그램은 각 입력을 출력으로 변환하는 **정책**을 상세하게 기술한 설명서다.
- **수준**이란 입/출력까지의 거리다. 입/출력 모두로부터 멀리 위치할수록 정책의 수준은 높아진다.
- 고수준 정책은 저수준 정책에 비해 덜 빈번하게 변경되고, 보다 중요한 이유로 변경되는 경향이 있다.

### 20장. 업무 규칙
- 업무 규칙 정의 : 구현 여부와 상관 없이, 사업적으로 수익을 얻거나 비용을 줄일 수 있는 규칙 혹은 절차.
- 엔티티
  - 정의 : 핵심 업무 규칙 & 핵심 업무 데이터로 이루어진 객체.
  - 특징 : DB, UI, 프레임워크 등에 오염되면 안 됨. POJO 권장.
- 유즈케이스
  - 정의 : 시스템이 동작하는 방식. 입력/출력/처리단계
  - 역할 : 엔티티 제어
- 업무 규칙은 UI, DB 같은 저수준 관심사로 인해 오염되어서는 안 되며, 원래 그대로의 모습으로 남아 있어야 한다.

### 21장. 소리치는 아키텍처
- 당신이 헬스 케어 시스템을 구축하고 있다면, 새로 들어온 프로그래머가 소스 저장소를 봤을 때 첫 인상은 "오, 헬스 케어 시스템이군" 이어야만 한다.

### 22장. 클린 아키텍처
- 엔터프라이즈 업무 규칙(엔티티) / 어플리케이션 업무 규칙(유즈케이스) / 인터페이스 어댑터(컨트롤러,프레젠터,게이트웨이) / 프레임워크와 드라이버(DB,UI,외부인터페이스,웹,장치)
- 소스 코드 의존성은 반드시 안쪽으로, 고수준의 정책을 향해야 한다. 즉, 내부 원에 속한 요소는 외부 원에 속한 어떤 것도 알지 못한다.
- 준수시 이점 : 테스트 용이. 외부 요소들 교체 쉬움.

### 23장. 프레젠터와 험블 객체
- 험블 객체 패턴 : 테스트 쉬운 행위, 어려운 행위를 나누고, 어려운 부분을 한곳(humble, 멍청한)으로 몰아두는 것.
- 아키텍처 경계에서 험블 객체 패턴을 사용하면 전체 시스템의 테스트 용이성을 높일 수 있음.

### 24장. 부분적 경계
- 클린아키텍처 구현 비용이 너무 크게 느껴진다면, 부분적 경계부터 시도해보자.
- 단일 패키지(or 모듈)로 구현하기 / 일차원(단방향) 경계 / 파사드



## 인상 깊은 내용
> 특히 기억에 남거나 공감된 부분
- 유즈케이스는 웹(e.g. HttpRequest, HttpResponse) 이나 SQL 에 대해 알지 못한다.
- 엔티티 객체를 가리키는 참조를 요청/응답 데이터 구조에 포함하려는 유혹이 들 수 있다.


## 이해가 어려웠던 내용
> 설명이 어렵거나 개념이 잘 이해되지 않았던 부분
- 197p. 정책에 대한 논의는 SRP, OCP, CCP, DIP, 안정된 의존성 원칙, 안정된 추상화 원칙을 모두 포함한다.
- 험블 객체 패턴. ORM.

```
domain/
  model/
    User.java
    UserId.java
    Email.java
  port/
    UserRepository.java

infrastructure/
  persistence/
    UserDocument.java        ← 험블 객체
    UserMapper.java          ← 데이터 매퍼
    MongoUserRepository.java ← Spring Data 인터페이스
    UserRepositoryImpl.java  ← 포트 구현체

application/
  usecase/
    GetUserUseCase.java
```
