## 핵심 내용 요약
- 컴포넌트 정의 : 컴포넌트는 시스템의 구성 요소로 배포할 수 있는 가장 작은 단위이다. e.g. jar 파일

### REP 재사용/릴리즈 등가 원칙 (Reuse/Release Equivalence Principle)
- 정의 : 재사용 단위는 릴리즈 단위와 같다.
- 하나의 컴포넌트로 묶인 클래스들은 함께 릴리즈 되어도 말이 되어야 한다.(make sense)
- 위반 예시

```
my-utils/
├── DateFormatter.kt      // 날짜 포맷 유틸
├── EmailValidator.kt     // 이메일 유효성 검사
├── ImageResizer.kt       // 이미지 리사이징
└── CsvParser.kt          // CSV 파싱
```

### CCP 공통 폐쇄 원칙 (Common Closure Principle)
- 동일한 시점에 동일한 이유로 변경되는 클래스들을 하나의 컴포넌트로 묶어라.
- 이 원칙을 준수하면 변경 범위가 하나의 컴포넌트로 몰리게 되어서 유지보수성이 좋아짐.

### CRP 공통 재사용 원칙 (Common Reuse Principle)
- 함께 재사용되는 경향이 있는 클래스들을 하나의 컴포넌트로 묶어라.
- 반대로 말해서, 강결합될 필요가 없는 클래스들을 하나의 컴포넌트로 묶지 말라. -> 클라이언트쪽에서 필요하지 않은 것에 의존하지 않을 수 있게 설계해라.

### 컴포넌트 응집도의 고차원적 이해.
- 프로젝트 초기 : 포함 원칙(REP, CCP)에 집중. 일단 monolithic 하게 만들어! -> 개발가능성은 높으나 재사용성은 낮음.
- 프로젝트 성숙기 : 배제 원칙(CRP) 에 집중. 별도 컴포넌트로 뺼 수 있으면 빼! -> 재사용성은 높으나 개발가능성은 낮음.
- 응집도의 1차원적 이해 : 모듈은 단 하나의 기능만 수행해야 함.
- 응집도의 2차원적 이해 : 재사용성 - 개발가능성과의 충돌 인지. 균형 추구.

### ADP 의존성 비순환 원칙
- 숙취 증후군 : 많은 개발자가 동일한 혹은 의존성 있는 소스코드를 수정하는 환경에서 충돌 발생. -> 빌드, 통합 비용 증가. -> 개발 속도 저하
- 해결책 : 프로젝트를 **릴리즈 가능한** 컴포넌트 단위로 나눠라. 
  - 전제 조건 : 컴포넌트 간 순환 의존성이 없어야 함.
- 컴포넌트 의존성 구조는 top-down 으로 설계할 수 없음. 컴포넌트 구조는 개발 과정 중 시시각각 바뀌기 때문임. 따라서 의존성 순환이 생기진 않았는지 수시로 점검해야 함.


### SDP 안정된 의존성 원칙 (Stable Dependencies Principle)
- 정의 : 변경이 쉬운 모듈이 변경이 어려운 모듈에 의존해라.
- 안정성 : 들어오는 의존성(fan-in) 이 많을수록 안정적이다.
- 불안정성(I) : fan-out / (fan-in + fan-out)
  - fan-in 은 없고, fan-out 만 많다 -> 마음껏 변경해도 됨. -> 불안정성(I) 가 높다. 
- 모든 의존성은 I 가 감소하는 방향으로 향해야 한다.

### SAP 안정된 추상화 원칙 (Stable Abstractions Principle)
- 정의 : 안정된 컴포넌트는 인터페이스, 추상클래스로 구성되어 쉽게 확장할 수 있어야 한다.
- 추상화 정도(A) - 안정성(I) 그래프 
  - (0,0) : concrete 클래스로 구성 & 안정성 높음(fan-in 많음) -> 확장성도 떨어지고 변경하는 것도 어려움. -> 배제하는 게 좋음
  - (1,1) : abstact 클래스로 구성 & 안정성 낮음(fan-in 적음) -> 추상화했지만 아무도 implement 하지 않음. -> 쓸모 없는 구역. 배제하는 게 좋음.
  - 컴포넌트는 배제 구역에서 떨어져 있는 (0,0) - (1,1) 사이에 가깝게 위치하는게 이상적.
