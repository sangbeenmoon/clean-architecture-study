## 현업 경험 공유
> 실제 업무에서 겪었던 경험이나 사례
- 마틴의 주장을 실무 언어로 번역하면 이렇습니다. "DB 선택은 해라. 다만 그 선택이 도메인 로직을 오염시키지 않게 경계를 그어라. 그러면 나중에 바꿔야 할 때 갈아끼울 수 있다." 그래서 실무자들은 보통 이렇게 받아들여요. DB 결정을 미루는 게 목표가 아니라, 미룰 수 있을 만큼 결합도를 낮추는 게 목표다. 결과적으로 결정을 미루지 않더라도 그 구조 자체가 유지보수성과 테스트 용이성을 크게 높여줍니다.
- "내일 갑자기 사장이 '우리 서비스 CLI로도 제공하자'고 하면, 비즈니스 로직 코드를 얼마나 고쳐야 하나?"
  - 거의 안 고쳐도 됨 → 웹을 세부사항으로 잘 분리한 것
  - 사실상 다시 짜야 함 → 웹과 비즈니스 로직이 엉켜있는 것

- 프레임워크와 결혼하지 않은 clean 한 구조 예시
```
com.shop
├── domain/          # 순수 자바. Spring 모름.
│   └── order/
├── application/     # 유스케이스. 포트 정의. Spring 모름(또는 최소).
│   └── order/
├── infrastructure/  # JPA, RestTemplate, Kafka 어댑터. Spring 안다.
│   └── persistence/
└── presentation/    # @RestController, @RequestMapping. Spring 안다.
    └── rest/
```
