## 핵심 내용 요약
### SRP (단일 책임 원칙)
- 정의 : 하나의 모듈은 오직 하나의 액터에 대해서만 책임져야 한다. 혹은 단일 모듈은 변경의 이유가 오직 하나뿐이어야 한다.
- 위반되고 있다는 징후
  - 하나의 클래스가 여러 액터를 책임지고 있음.
  - 여러 개발자가 서로 다른 이유가 동일한 소스 파일을 변경 -> conflict 발생
- 해결 방안
  - 액터(요구사항) 별로 클래스를 분리.
  - 클래스가 많아지는게 부담이라면 Facade 패턴 사용.

### OCP (개방 폐쇄 원칙)
- 정의 : 기존 코드를 수정하기보다는 새로운 코드를 추가하는 방식으로 시스템의 행위를 변경할 수 있도록 설계해야만 소프트웨어 시스템을 쉽게 변경할 수 있음.
- 예시 : 재무 데이터 생산 - 데이터 출력 책임을 분리하고, 데이터 출력 요구사항이 들어왔을 때는 저수준의 데이터 출력 클래스만 추가해서 요구사항을 만족할 수 있어야 함.
- OCP 를 준수하기 위한 방법
  - 시스템을 *계층을 가진* 컴포넌트 단위로 분리하고(e.g. Interactor, Controller, Presenter, View), 저수준의 컴포넌트에서 발생한 변경으로부터 고수준 컴포넌트를 보호.

## LSP (리스코프 치환 원칙)
- 정의 : 상호 대체 가능한 구성요소를 이용해 소프트웨어 시스템을 만들 수 있으려면, 이들 구성요소는 반드시 치환 가능해야 한다.
- 예시 : Interface 를 구체 클래스로 대체할 수 있음.
- 반례 : 정사각형/직사각형 문제
- 단지 클래스 레벨뿐만이 아니라 API 레벨에서도 LSP 를 적용할 수 있음. 

## ISP (인터페이스 분리 원칙)
- 정의 : 클라이언트(소프트웨어 설계자)는 사용하지 않은 것에 의존하지 않아야 한다.
- 예시

```java
interface Worker {
    void work();
    void eat();
}

class HumanWorker implements Worker {
    @Override
    public void work() {
        System.out.println("Human working");
    }

    @Override
    public void eat() {
        System.out.println("Human eating");
    }
}

class RobotWorker implements Worker {
    @Override
    public void work() {
        System.out.println("Robot working");
    }

    @Override
    public void eat() {
        // ❌ 로봇은 먹지 않는데 구현 강제됨
        throw new UnsupportedOperationException("Robot doesn't eat");
    }
}
```

## DIP (의존성 역전 원칙)
- 정의 : 고수준 정책을 구현하는 코드는 저수준 세부사항을 구현하는 코드에 절대로 의존해서는 안된다. 대신 세부사항이 정책에 의존해야 한다.
- 구체 클래스 보다는 추상 클래스에 의존하라. 단, 안정성이 보장된 구체 클래스에 의존하는 것은 괜찮다. e.g. java.lang.String
- DIP 를 준수하는 클래스 다이어그램을 그리고 나면 추상 클래스 - 구체 클래스 사이 의존성 경계가 생기는데, 이것이 바로 아키텍처 경계이다. (추후 다룰 예정.)

## 인상 깊은 내용
> 특히 기억에 남거나 공감된 부분
- LSP 는 아키텍처 수준까지 확장할 수 있고, 반드시 확장해야만 한다. 치환 가능성을 조금이라도 위배하면 시스템 아키텍처가 오염되어 상당량의 별도 메커니즘을 추가해야할 수 있기 때문이다.
- 필요 이상으로 많은 걸 포함하는 모듈에 의존하는 것은 해로운 일이다. (ISP)
- 상속은 아주 신중하게 사용해야 한다. 상속은 가장 강력한 동시에 가장 뻣뻣해서 변경하기 어렵다. (DIP)
